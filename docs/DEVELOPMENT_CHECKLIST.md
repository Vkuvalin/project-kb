# Контрольный список разработки Project KB

## 1. Как использовать этот список

Это стабильный список контрольных пунктов для разработки и публикации, а не журнал работ и не
историческая матрица. Не каждый пункт применим к каждому изменению: перед принятием
изменения отметьте все затронутые контрольные пункты и зафиксируйте неприменимые границы явно.

Технические владельцы деталей — [архитектура](ARCHITECTURE.md) и
[политика безопасности данных](DATA_SAFETY_POLICY.md). Состояние «заморожен» означает, что новые
продуктовые границы требуют отдельного явного решения; их нельзя добавлять незаметно
через расширение этого списка.

## 2. Перед изменением продукта

- [ ] Определена точная цель изменения и перечислены затронутые публичные и внутренние
  поверхности.
- [ ] Подтверждено, что изменение относится к сопровождению замороженного Project KB, а не
  расширяет продуктовые границы.
- [ ] В [архитектуре](ARCHITECTURE.md) найден текущий компонент и владелец
  затрагиваемой ответственности.
- [ ] В [политике безопасности данных](DATA_SAFETY_POLICY.md) найдена применимая нормативная
  граница записи, чтения, идентичности или актуальности.
- [ ] Неподдерживаемые флаги возможностей сохраняются выключенными, пока поддержка не
  одобрена и не реализована отдельно.
- [ ] В изменение не смешаны несвязанная очистка, работа над экспериментальным стендом и продуктовые
  изменения.
- [ ] Публичный результат не зависит от приватного пути, локальной среды или
  непереносимого пользовательского предположения.

## 3. Хранилище, идентичность и актуальность

- [ ] Репозиторий исходников остаётся входом только для чтения: продукт не изменяет рабочее дерево,
  текущее хранилище Git или целевой код и не выполняет код целевого проекта.
- [ ] Тесты и ручная проверка, способные менять состояние, используют отдельный
  `PROJECT_KB_HOME` и безопасный тестовый репозиторий, а не реальную регистрацию и
  управляемое хранилище пользователя.
- [ ] Каноническая идентичность проекта и привязка реестра через рабочую копию `PRIMARY`,
  идентичность репозитория и поколение привязки остаются явно связанными и проверяемыми.
- [ ] Канонический снимок проходит захват, проверку и закрытие до атомарной
  публикации; ответственность поколения/жизненного цикла не обходится, а управляемые поколения
  остаются отдельными однократно создаваемыми артефактами.
- [ ] Структурная читаемость снимка не используется как доказательство актуальности:
  доступность и актуальность проверяются раздельно.
- [ ] `STALE` и `UNVERIFIED` не представляются как `CURRENT`; `CURRENT` относится только
  к моменту подтверждённого `verified_at`.
- [ ] Реализованная преемственность между снимками внутреннего жизненного цикла сохраняет согласованные
  ответственность задач, родительские связи, последовательность поколений и указатели и не выдаётся за
  публичную возможность CLI/MCP.
- [ ] Секреты, локальные абсолютные пути и несвязанные данные репозитория не попадают в
  постоянные или публичные артефакты.

Нормативные детали этих инвариантов принадлежат
[политике безопасности данных](DATA_SAFETY_POLICY.md), а не этому списку.

## 4. Поверхности CLI и MCP

### CLI

- [ ] Упаковка по-прежнему устанавливает `pkb`, `project-kb` и `pkb-mcp`; изменение
  любой точки входа сверено с `pyproject.toml`, исходниками и целевыми тестами.
- [ ] При изменении CLI проверены `uv run pkb --help`,
  `uv run project-kb --help`, справка изменённой команды и её контракт исходников/тестов.
- [ ] `symbols`, `imports` и `inspect` остаются ограниченными структурными запросами, отличными
  от неподдерживаемого обобщённого/семантического поиска; внутренний жизненный цикл не получает
  неявную публичную команду.
- [ ] Вывод `capabilities` и доступность соответствуют реализации: `search`,
  `exports`, `context_packs`, `can_search`, `can_generate_exports` и
  `can_generate_context` остаются выключенными.

### MCP

- [ ] `pkb-mcp` остаётся постоянной точкой входа `stdio` и требует полный
  контракт закреплённой оператором идентичности: путь, идентификаторы проекта и снимка, SHA-256 и коммит
  исходников; неполная или противоречивая конфигурация останавливает запуск.
- [ ] MCP обслуживает ровно закреплённый снимок и не выбирает другой артефакт,
  поколение `latest` или состояние текущего реестра.
- [ ] Структурные запросы данных открывают SQLite через `mode=ro`, `immutable=1` и
  `query_only`; транспорт не публикует снимки и не меняет указатели или актуальность.
- [ ] Аннотации инструментов и фактическое поведение остаются предназначенными только для чтения и структурными;
  изменение состава требует синхронного обновления архитектуры, README и целевых
  тестов MCP.

## 5. Контрольные пункты проверки

- [ ] Требование Python `>=3.14`, зависимости в `pyproject.toml` и `uv.lock` согласованы;
  при изменении зависимостей выполнены `uv lock --check` и `uv sync --locked`.
- [ ] Запущены целевые тесты ответственности, затронутой изменением, без подмены
  реального контракта чрезмерными имитациями или фикстурами.
- [ ] Полный текущий набор тестов проходит командой `uv run pytest`.
- [ ] Формат и статический анализ проходят командами `uv run ruff format --check .` и
  `uv run ruff check .`.
- [ ] При изменении точек входа, CLI или MCP дополнительно проверены справка, установленные
  команды и соответствующие тесты контрактов CLI/MCP, включая `pkb-mcp`.
- [ ] Любая изменяющая состояние проверка использует изолированное управляемое хранилище; репозиторий
  исходников и реальный домашний каталог Project KB остаются неизменными.
- [ ] Проверка по умолчанию не выполняет сетевые вызовы или обращения к поставщикам и не запускает
  исторические эксперименты стенда.
- [ ] Выполнены `git diff --check`, просмотр точных изменений и итоговая проверка
  `git status` на незаявленные границы.

  техническое руководство.
- [ ] [Архитектура](ARCHITECTURE.md) остаётся владельцем текущих компонентов, потоков и
  границ ответственности.
- [ ] [Политика безопасности данных](DATA_SAFETY_POLICY.md) остаётся владельцем нормативных
  инвариантов записи/чтения, идентичности и актуальности.
- [ ] [Методология экспериментального стенда](BENCHMARK.md) владеет методикой,
  [эксперименты и результаты](EXPERIMENTS_AND_RESULTS.md) — измерениями и исправлениями, а
  [история разработки](DEVELOPMENT_HISTORY.md) — курируемой исторической преемственностью.
- [ ] Публичные документы не содержат служебные пути автоматизации, локальные
  абсолютные пути, секреты, приватные значения среды или расположения сохранения.
- [ ] Все добавленные и затронутые публичные ссылки разрешаются в существующие файлы

- [ ] Позиционирование замороженной реализации для портфолио и справочного примера остаётся точным, а неподдерживаемые

- [ ] Официальный выпуск или готовность лицензии заявляется только после появления
  соответствующих метаданных, лицензии и подтверждённой публичной чистоты.

## 7. Граница исторических экспериментов

- [ ] Каноническое историческое оценивание не переписано и не заменено задним числом.
- [ ] Диагностика и исправления остаются явно отделены от канонических результатов и не называются
  новым официальным оцениванием.
- [ ] Запуски стенда не входят в обычную проверку для участников разработки и продукта.
- [ ] Документация не утверждает существование формальной N5 или G3: N5 не была завершена,
  а G3 не создавался.
- [ ] Остановленное расширение остаётся остановленным, пока отдельно не одобрено новое
  поколение эксперимента.
- [ ] Исторические наблюдения остаются ограниченными конкретными задачами и средой;
  приёмка текущего продукта не выводится из одной таблицы оценок.

Подробные границы принадлежат [методологии экспериментального стенда](BENCHMARK.md) и
[экспериментам и результатам](EXPERIMENTS_AND_RESULTS.md); массивы оценок и методика здесь не
повторяются.
