# Политика безопасности данных Project KB

Этот документ — нормативный владелец правил безопасного обращения Project KB с репозиторием исходников, Git, реестром, снимками и локальным управляемым хранилищем. Обзор компонентов и потоков принадлежит [архитектуре Project KB](ARCHITECTURE.md); здесь фиксируются только разрешения, запреты, инварианты и условия отказа.

## 1. Границы действия

Политика распространяется на:

- регистрацию, `relink` и `unregister` проектов;
- чтение репозитория исходников и метаданных Git;
- канонический захват, публикацию и структурное чтение;
- внутренние операции жизненного цикла и управляемые поколения;
- получение состояния и проверку актуальности;
- замороженное чтение через MCP закреплённого оператором снимка;
- все пути внутри `<PROJECT_KB_HOME>`.

Политика не даёт разрешения изменять репозиторий исходников и не расширяет замороженный контракт возможностей. Обобщённый поиск, генерация экспорта и пакета контекста остаются недоступными.

## 2. Модель доверия и ответственности

Репозиторий исходников, его файлы, метаданные Git и перенаправления файловой системы считаются недоверенным входом. Project KB может извлекать из них структурные факты, но не получает права владения деревом исходников.

`<PROJECT_KB_HOME>` — единственная управляемая граница записи продукта. Сервис реестра владеет состоянием контура управления. Канонический `IndexService` владеет текущим снимком отдельного проекта. Внутренний сервис поколений жизненного цикла владеет однократно создаваемыми файлами поколений и связанными записями реестра. Замороженный транспорт MCP не владеет читаемым артефактом и не имеет права его изменять.

Доверие к снимку определяется проверенной идентичностью, а не только именем или расположением файла. Для текущего канонического контура необходимы активная привязка проекта и рабочей копии и метаданные снимка. Для замороженного контура MCP необходим полный контракт закреплённой оператором идентичности.

## 3. Разрешённые постоянные записи

Project KB MUST ограничивать постоянные записи следующими управляемыми расположениями:

| Управляемое расположение | Разрешённые записи |
| --- | --- |
| `<PROJECT_KB_HOME>/registry.sqlite` | Создание и транзакционное обновление реестра v4; принадлежащие SQLite временные сопутствующие файлы транзакций рядом с базой |
| `<PROJECT_KB_HOME>/projects/<project_id>/` | Создание только корневого каталога хранилища проекта; строка не разрешает произвольные постоянные дочерние элементы |
| `<PROJECT_KB_HOME>/projects/<project_id>/kb.sqlite` | Атомарная каноническая публикация |
| `<PROJECT_KB_HOME>/projects/<project_id>/runs/` | Канонические записи запусков и принадлежащие операции временные файлы снимков |
| `<PROJECT_KB_HOME>/projects/<project_id>/exports/` | Только контейнер хранилища; его наличие не разрешает генерацию экспорта |
| `<PROJECT_KB_HOME>/generations/<shard>/<snapshot_id>.sqlite` | Однократная публикация управляемого поколения |
| Каталог управляемого поколения рядом с конечным файлом | Только принадлежащий текущей операции временный файл поколения и необходимые сопутствующие файлы SQLite до очистки/публикации |
| `<PROJECT_KB_HOME>/scratch/currentness/` | Родительский каталог и очищаемые временные каталоги отдельных проверок |

Создание управляемых каталогов разрешено только для явно перечисленных принадлежащих продукту расположений или как создание необходимых родительских каталогов этих точных расположений; это не даёт общего разрешения на произвольные постоянные дочерние элементы. Внутри хранилища проекта постоянные дочерние записи ограничены `kb.sqlite`, `runs/`, контейнером `exports/` и иными проверенными по исходникам принадлежащими продукту путями, только если они прямо перечислены в этой политике. Любая запись в репозиторий исходников, его хранилище `.git` или произвольный внешний путь MUST NOT выполняться.

Поиск состояния через механизм разрешения, предназначенный для чтения существующего состояния, MUST NOT создавать отсутствующие управляемый домашний каталог, реестр или хранилище проекта. Их создание принадлежит явным изменяющим операциям, таким как `register`.

## 4. Безопасность репозитория исходников

При захвате и проверке актуальности Project KB MUST:

- обращаться с репозиторием как со входом только для чтения;
- формировать совокупность из отслеживаемых Git и неотслеживаемых, не игнорируемых путей с ограниченным обнаружением по политике;
- читать содержимое только допустимого обычного текстового файла после проверок пути и идентичности;
- не импортировать, не выполнять и не загружать код целевого проекта как плагин;
- сохранять структурные производные данные, а не дословное содержимое исходников;
- представлять символическую ссылку, junction, reparse point и иное перенаправление только метаданными, не переходя к содержимому цели;
- повторно проверять доказательства файловой системы и исходников там, где чтение может участвовать в доказательстве стабильности.

Двоичные данные, слишком большие файлы, неподдерживаемые расширения и кодировки остаются только метаданными. Поддерживаемые исходники Python разбираются стандартным синтаксическим анализатором AST из текста; целевой модуль при этом не импортируется. Ошибка разбора отдельного допустимого файла может быть записана как структурный факт, но не разрешает обход проверок безопасности. Неустойчивое состояние исходников не может считаться доказанным стабильным захватом.

## 5. Правила изоляции Git

Исполнитель Git MUST принимать только явно разрешённые вызовы для чтения и MUST отключать постраничный вывод, хуки, отложенную загрузку и необязательные блокировки там, где это задаёт текущий контракт исполнителя. Неожиданные аргументы или подкоманды должны отклоняться до запуска Git.

Единственная имеющая форму записи операция Git, используемая для доказательства совокупности, — `update-index --index-info` с отдельным временным `GIT_INDEX_FILE`. Этот индекс MUST находиться вне репозитория исходников, MUST быть очищен владельцем операции и MUST NOT заменять или изменять текущий индекс Git.

Захват, проверка актуальности и структурный запрос MUST NOT изменять рабочее дерево, текущее хранилище Git, ссылки, индекс или конфигурацию репозитория. Окружение Git очищается от переменных, способных перенаправить операцию в иной репозиторий или включить внешнее выполнение.

`remote.origin.url` может читаться только локальной разрешённой командой без подключаемых файлов конфигурации и немедленно сводится к SHA-256 в отпечатке репозитория. Постоянное состояние MUST хранить хеш, а не исходный URL. Эти наблюдения MUST NOT выполнять загрузку или обращаться к удалённому репозиторию.

## 6. Обработка путей и секретов

Все пути относительно репозитория MUST пройти нормализацию и проверки вложенности. Абсолютные пути, обход пути, NUL, выход из корневого каталога и смена идентичности родительского/конечного файла должны приводить к отказу или безопасной классификации «только метаданные». Безопасное чтение обычного файла использует доказательства идентичности до и после операции и семантику без перехода по ссылкам, когда платформа её предоставляет.

Принадлежащие Project KB пути домашнего каталога, хранилища проекта и реестра MUST быть каноническими, вложенными, неперенаправленными и ожидаемого типа. Канонический снимок MUST быть обычным неперенаправленным файлом в точном хранилище проекта. Закреплённый оператором снимок MCP также должен быть обычным неперенаправленным файлом, но не обязан принадлежать управляемому домашнему каталогу.

Конечное управляемое поколение MUST находиться в детерминированном корневом каталоге поколений и быть обычным неперенаправленным файлом с одной идентичностью жёсткой ссылки; перенаправленное поколение или файл с несколькими жёсткими ссылками отклоняется.

Известные жёстко запрещённые базовые имена и суффиксы секретов MUST классифицироваться до открытия содержимого. Для них разрешены только метаданные, без хеша содержимого. Явно безопасные имена шаблонов могут обрабатываться как обычный текст. Эти правила являются ограниченной политикой, а не обещанием обнаружить произвольный секрет по смыслу; правила игнорирования Git и формирования совокупности продолжают применяться независимо.

Ошибки и пользовательский вывод не должны раскрывать прочитанное содержимое секрета. Конфигурация закреплённого MCP документируется только именами переменных и значениями-заполнителями.

## 7. Инварианты захвата и канонической публикации

Нейтральный к публикации захват MUST закрепить идентификатор проекта, идентичность рабочей копии `PRIMARY`, нормализованный корневой путь, идентичность репозитория и поколение привязки до чтения. Временный файл назначения MUST быть новым, принадлежать операции и находиться вне репозитория исходников.

Захват может вернуть закрытый дескриптор только после:

1. получения допустимой совокупности Git;
2. безопасного ограниченного сканирования;
3. записи семантической схемы снимка v2;
4. полной проверки и закрытия снимка;
5. проверки итоговых доказательств состояния исходников;
6. повторного подтверждения активной привязки.

Канонический `IndexService` MUST публиковать только такой закрытый снимок. Конечный `kb.sqlite` заменяется атомарно; успешное обновление учётных данных реестра выполняется после замены, а опубликованный снимок затем снова сопоставляется с активной привязкой.

До атомарной замены любая ошибка MUST сохранять прежние канонические байты и очищать принадлежащие операции временные артефакты. Если привязка меняется после замены, операция MUST завершиться отказом, а новый канонический снимок MUST считаться изолированным и непригодным к использованию. В этой точке политика не обещает возврат прежних байтов.

Каноническое структурное чтение MUST открывать снимок только для чтения, требовать `can_use_snapshot` и перепроверять активную привязку и идентичность снимка на границе запроса. Читаемость снимка не разрешает обобщённый поиск.

## 8. Инварианты реестра v4 и активной привязки

Текущая версия схемы реестра равна **4**. Реестр v4 MUST хранить авторитетную идентичность физической рабочей копии в её записи. Для каждого проекта MUST существовать ровно одна рабочая копия `PRIMARY`; поля корневого пути, репозитория и привязки проекта являются согласованной проекцией совместимости.

Инициализация и миграция реестра MUST быть транзакционными, проверять точную схему и завершаться отказом при неоднозначной или несовместимой идентичности. Запись выполняется короткими транзакциями `BEGIN IMMEDIATE` с контролем внешних ключей. Путь реестра должен указывать на обычный неперенаправленный файл внутри управляемого домашнего каталога.

Активная привязка определяется совокупностью идентификатора проекта, рабочей копии `PRIMARY`, нормализованного корневого пути, идентичности репозитория и поколения привязки. `relink` MUST создавать новое поколение привязки, даже если корневой путь совпадает с ранее использованным, и MUST переводить канонический снимок в состояние, требующее повторной индексации. `relink` при открытой работе жизненного цикла или неразрешённой операции должен отказываться.

Канонические захват, учёт публикации и чтение MUST совпадать с активной привязкой. Несовпадение привязки делает снимок недоступным или несовместимым независимо от корректности его схемы SQLite. `unregister` MUST использовать проверку идентичности/CAS и ограничивать удаление точным корневым каталогом хранилища проекта; полное удаление при наличии записей жизненного цикла не допускается.

## 9. Инварианты публикации управляемого поколения

Управляемые поколения принадлежат внутреннему контуру жизненного цикла и MUST оставаться отделены от канонического `kb.sqlite`. Каноническая индексация не создаёт записи жизненного цикла; публикация жизненного цикла не заменяет канонический файл, не изменяет репозиторий исходников и не использует ответственность канонических запусков.

Публикация поколения MUST выполняться по схеме «сначала файл»:

1. операция резервирует идентичность и детерминированный конечный путь;
2. закрытый временный снимок проверяется по схеме, идентификатору снимка, размеру, хешу и свидетельству;
3. конечный файл создаётся один раз без перезаписи;
4. конечные байты и идентичность проверяются повторно;
5. только затем транзакция реестра регистрирует поколение `AVAILABLE`, обновляет ожидаемый указатель через CAS и завершает операцию.

Существующий конечный путь с иной идентичностью, жёсткой ссылкой/перенаправлением, несовпадающим хешем или конфликтом CAS указателя MUST приводить к отказу. Если файл уже опубликован, а завершение в реестре не может безопасно выполниться, состояние должно быть зарегистрировано как осиротевшее с отказом по умолчанию; перезапись или незаметный откат запрещены.

Псевдоним селектора MUST сначала разрешаться в точный идентификатор снимка. Чтение точного поколения MUST повторно проверить запись реестра, идентичность обычного файла с одной ссылкой, размер, SHA-256 и метаданные снимка. После смены активной привязки точный исторический идентификатор может оставаться явно адресуемым, но псевдоним и проверка актуальности не должны молча переноситься на новую привязку.

## 10. Границы актуальности и проверки

Актуальность — отдельная ось, не синоним доступности. Допустимые результаты: `CURRENT`, `STALE`, `UNVERIFIED`, `CHANGED_DURING_CHECK` и `ERROR`.

Режим `fast` удалён: запрос такого режима MUST вернуть `UNVERIFIED` с причиной `fast_verification_removed` и без `verified_at`. Строгая проверка использует ограниченное число попыток, стабильные наблюдения, доказательство снимка и проверки привязки. Только `CURRENT` разрешает утверждение о достоверности `CURRENT_AT_VERIFIED_TIME`.

`CURRENT` действует как утверждение о моменте `verified_at` и MUST NOT трактоваться как бессрочная гарантия свежести. Изменение исходников или привязки во время проверки приводит к `CHANGED_DURING_CHECK`, `STALE` либо отказу по умолчанию в зависимости от доказательств.

Совместимый снимок `UNVERIFIED` или `STALE` может оставаться структурно читаемым, поэтому `can_use_snapshot=true` не означает актуальность. Операция, требующая актуальный снимок, MUST отдельно применить проверку `SNAPSHOT_CURRENT`. Ни доступность, ни актуальность не включают `can_search`, `can_generate_exports` или `can_generate_context`.

## 11. Безопасность замороженного транспорта MCP

`pkb-mcp` MUST получить полный контракт закреплённой идентичности через следующие переменные окружения:

```text
PKB_MCP_SNAPSHOT_PATH=<snapshot-path>
PKB_MCP_PROJECT_ID=<project-id>
PKB_MCP_SNAPSHOT_ID=<snapshot-id>
PKB_MCP_SNAPSHOT_SHA256=<64-hex-sha256>
PKB_MCP_SOURCE_COMMIT=<git-commit>
```

Отсутствующая или некорректная переменная должна остановить запуск. При запуске сервер MUST ровно один раз вычислить SHA-256 всего файла и проверить ожидаемые хеш, идентификаторы проекта и снимка, коммит исходников и семантическую схему снимка. Этот полный хеш не вычисляется заново для каждого запроса.

Каждый структурный запрос данных MUST открывать отдельное соединение SQLite с `mode=ro`, `immutable=1` и `PRAGMA query_only = ON`, устанавливать ограничение выполнения виртуальной машины и повторно проверять идентификатор снимка при настройке. Инструмент метаданных использует закреплённое при запуске состояние без нового запроса SQLite. Записи, фильтры, значения, пути, курсор и размер ответа ограничиваются; наборы данных, столбцы и фильтры берутся только из списка разрешённых значений.

Инструменты MCP предназначены только для чтения и MUST NOT публиковать файлы, изменять SQLite, разрешать данные через текущий реестр, выбирать последнее поколение, менять указатель или заявлять актуальность. Аннотации «только для чтения» дополняют, но не заменяют фактические ограничения SQLite и запросов. Между запросами сервер доверяет закреплённому контракту неизменяемого артефакта; повторное хеширование всего файла для каждого запроса не обещано.

## 12. Правила ошибок и отказов

| Условие | Обязательная реакция |
| --- | --- |
| Операция чтения требует существующий реестр, но он отсутствует, имеет неверную схему или неоднозначную идентичность | Отказ без частичной миграции/записи; явная инициализация через `register` остаётся отдельной операцией |
| Рабочая копия `PRIMARY`, идентичность репозитория или привязка не совпадают | Снимок недоступен; публикация/чтение не продолжаются |
| Исходники или привязка меняются во время захвата/проверки | Повтор в заданных пределах либо `CHANGED_DURING_CHECK`/отказ |
| Путь выходит из корневого каталога, перенаправлен или меняет идентичность | Не читать содержимое цели; отказ или классификация «только метаданные» |
| Путь распознан как жёстко запрещённый секрет | Не открывать содержимое и не вычислять хеш содержимого |
| Захват, сборка или закрытие ошибается до канонической замены | Очистить принадлежащие операции временные артефакты; сохранить прежний канонический файл |
| Привязка меняется после канонической замены | Отказ и логическая изоляция нового снимка; прежние байты не гарантируются |
| Конечный путь поколения занят, хеш/идентичность не совпадает или CAS проигран | Не перезаписывать; отказать по умолчанию, при необходимости зарегистрировать осиротевшее состояние |
| Конфигурация MCP, хеш при запуске или закреплённые метаданные не совпадают | Сервер/запрос не запускается |
| Структурный запрос нарушает список разрешённых значений или ограничение ресурсов | Детерминированный отказ без расширения доступа |

При отказе сохраняется наиболее узкое доказанное утверждение о достоверности. Ошибка не повышает доступность, актуальность или возможности.

## 13. Обязательства по проверке

Изменение реализации, затрагивающее эту политику, должно подтверждаться текущими инвариантами на уровне исходников и целевыми тестами безопасности. Минимальная проверка включает:

- версию схемы реестра и проверки миграции/активной привязки;
- отсутствие записи в репозиторий исходников и текущее хранилище Git;
- классификацию секрета до чтения содержимого, перенаправления и соблюдение вложенности;
- сохранение канонического файла до публикации и границу изоляции после публикации;
- публикацию поколения по схеме «сначала файл» с однократным созданием, хешем и CAS указателя;
- раздельную семантику доступности, актуальности и возможностей;
- идентичность замороженного MCP при запуске, режим SQLite только для чтения, списки разрешённых значений и ограничения;
- точную проверку фактически изменённых файлов и отсутствие незаявленных расположений записи.

Документационное изменение сохраняет этот файл нормативным владельцем безопасности, а [архитектуру Project KB](ARCHITECTURE.md) — владельцем карты компонентов и потоков среды выполнения в текущем состоянии. Примеры конфигурации используют заполнители и не содержат локальные пользовательские пути или значения секретов.
